# Texts and translations (i18n)

For projects with user-visible texts in more than one language, or libraries whose texts projects translate.

## 1. Where texts live

- No hard-coded user-visible text in views, templates, forms, tables, emails or exceptions shown to users. Every text
  comes from one place per language: message classes (typed properties, one class per area) or the translation files
  of the framework.
- One default language (usually English) is complete; every other language provides the same set of texts. A test
  checks that every language has every text.
- Texts shared by several areas live in one shared place, not as copies.

## 2. Format

- Messages are plain text without HTML. They are escaped when they are output (see [security.md](security.md),
  section 3); markup is built around them in the template or view.
- Punctuation that belongs to the sentence or label (`Success:`, `?`) is part of the message, so every language can
  place it correctly.
- Dynamic parts are named placeholders (`[email]`, `{count}`), never concatenated sentence fragments. Every language
  uses the same placeholders; a test checks it.
- Plurals, dates, numbers and currencies are formatted for the locale (`IntlDateFormatter`, `NumberFormatter`), not
  by hand.

## 3. Language at runtime

- The language of a request is chosen once (route, user setting or `Accept-Language`) and passed on; code does not
  cache texts of another language or build links with a fixed language.
- Texts for another person (e.g. an email to another user) use that person's language, not the language of the
  current request.
- The `lang` attribute of the HTML document matches the language of the texts.
